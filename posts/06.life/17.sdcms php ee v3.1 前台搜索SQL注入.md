Vulnerability Type: SQL Injection (Time-based Blind)  
Affected Version: SDCMS PHP EE 3.1  
Entry Point: `index.php?m=home&c=other&a=search`  
Privilege Required: Anonymous front-end access  
Test Environment: PHP 7.4.3, MySQL 5.7.26  
Verification Status: Reproduced locally; the vendor released a patched version on 2026-11-08.

## 1. Vulnerability Overview

The front-end search function in SDCMS PHP EE 3.1 is vulnerable to SQL injection. The user-supplied `keyword`, after parameter processing, is concatenated directly into the SQL query. An unauthenticated attacker can craft malicious input and infer the result of the SQL query from the response time.

Local testing confirmed the time-based blind injection and retrieved the database name, version, and the administrator's password hash.

## 2. Vulnerability Analysis

The flaw resides in the `search()` method of `app/home/controller/other.php`:

```php
$where  = "islock=1";
$where .= " and (";
$where .= " title like '%{$keyword}%' or intro like '%{$keyword}%' ";
$where .= ")";

$rs = $this->db->row(
    "select id from sd_content $join where $where order by id desc limit 1"
);
```

`$keyword` is inserted directly into the `LIKE` clause and then executed by the database as part of the SQL statement. No prepared statement is used, and the search term is not passed through parameter binding.

### Parameter Processing

The search parameter is obtained through `F()`, which invokes processing functions such as `filter_html()` and `enhtml()`; `enhtml()` performs URL decoding and HTML special-character conversion. In the POST branch, the controller calls `urldecode()` once more before storing the keyword in the session.

The test request flow is as follows:

1. A POST request submits the keyword; PHP form parsing, `enhtml()`, and the controller's `urldecode()` process the parameter in sequence.
2. The controller writes the processed keyword into the session.
3. A subsequent GET request reads the keyword from the session and executes `urldecode()` once again.
4. The decoded keyword is then passed into the search SQL.

The test script URL-encodes the payload three times, corresponding to the three decoding passes in the POST stage. The GET stage decodes the session content one more time. This encoding scheme applies to the POST/Session/GET request pattern used in this article; submitting the payload directly as a GET parameter follows a different processing path.

The `htmlspecialchars()` handling in the project is intended for HTML special-character conversion and does not prevent SQL injection. Although the database class also performs keyword replacement and `filter_char()` processing, the current call graph shows that `filter_char()` is not applied to this search query.

## 3. Verification

### Prerequisites

The search statement includes the condition `islock=1`, so the `sd_content` table must contain matching published content for this time-based blind test. A fresh installation contains no such records by default, and an administrator must add a content record manually.

### Time-based Blind Injection

The test script first saves the payload via POST, then issues a GET request carrying the same session cookie and measures the GET request latency. Submitting the payload below through the front-end search box causes the site to take several seconds before returning a response, confirming that the `sleep` function executed.

**Note: The payloads below are intended solely for local vulnerability verification. The vendor has fixed this issue in the latest release.**

Submit the following payload in the front-end search box:

```payload
%2527%2520and%2520sleep%25282%2529%2520and%25201%2520like%2520%2527
```

Alternatively, send the following request with Burp Suite (replace the parameters manually):

```http
POST /?m=search HTTP/1.1
Host: <Your_Host>:8080
Content-Type: application/x-www-form-urlencoded
Content-Length: 153
Cookie: PHPSESSID=<Your_SESSION_ID>
Connection: close

c=other&a=search&token=<Your_TOKEN>&keyword=%252527%252520and%252520sleep%2525282%252529%252520and%2525201%252520like%252520%252527
```

## 4. Impact

- Unauthenticated users can trigger front-end search queries.
- Response time can be used to infer the result of SQL expressions.
- Local testing retrieved the database name, version information, and the administrator password hash.

The direct consequence of this vulnerability is the disclosure of sensitive data. Under specific conditions, the impact can escalate further: if the administrator uses a weak password, an attacker could crack the hash offline to recover the plaintext password and log into the admin panel. By leveraging the template editing feature to modify and execute PHP code, the attacker could ultimately achieve Remote Code Execution (RCE).

## 5. Remediation

- Convert the search query to a prepared statement and pass the keyword through parameter binding.
- Review and remove redundant `urldecode()` calls, and specify clearly at which layer the parameter is decoded.
- Do not substitute HTML escaping or SQL keyword blacklists for SQL parameter binding.
- Restrict dynamic table names, column names, and sort order with an allowlist.
- Audit the rest of the project for other locations where user input is concatenated into SQL.

## 6. Patch Status

**After receiving the report, the vendor released a new version on 8 November 2026 that fixes this issue. The patched version was available for download at the time of publication.**
