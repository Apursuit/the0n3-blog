## 什么是 XSS 攻击

XSS（Cross Site Scripting，跨站脚本攻击）是指：
当目标网站在渲染 HTML 文档时，执行了**不被预期的恶意脚本**，就发生了 XSS。

简单来说：
攻击者通过输入点注入恶意 JavaScript，当其他用户（或 Bot）浏览页面时，脚本在其浏览器中执行，从而窃取 Cookie、模拟操作甚至控制账户。

XSS 常见三类：
- **反射型 XSS**：代码在 URL 中，服务器“反射”回页面
- **存储型 XSS**：代码被存储到服务器（如数据库），持续生效
- **DOM 型 XSS**：完全在客户端 DOM 解析阶段触发，服务器无感知

我主要有两点疑惑：
1.在 CTF 题目中，XSS 到底是如何被触发的？
2.通过 XSS 获取的 Cookie，通常是哪个用户的身份？

## XSS 常见标签与触发方式

常见可用于 XSS 的标签包括：

- `<script>`
- `<img>`
- `<svg>`
- `<iframe>`
- `<video>`
- `<a>`
- `<details>`
- `<marquee>`
- `<embed>`

常见触发方式：

- 事件触发：`onclick`、`onmouseover`、`onmouseout`、`onfocus`、`onerror`
- 函数/属性触发：`onload`、`window.open`、`window.location`

## 为什么需要 XSS Bot？

在 CTF 的 XSS 题目中，攻击者注入的 payload 通常不会被自己触发，
而是需要**特定用户（如管理员）访问页面**时才会执行。

因此，题目环境通常会提供一个 XSS Bot：

- 模拟管理员或其他高权限用户
- 自动访问包含 payload 的页面
- 从而触发 XSS，泄露该用户的 Cookie 或敏感信息


### XSS Bot 的触发流程

- 攻击者在输入点（评论、留言、表单等）注入恶意 JavaScript
- payload 被保存到服务器（存储型 XSS）
- XSS Bot 模拟管理员访问该页面
- Bot 的浏览器加载页面并执行 JavaScript
- 攻击者成功获取 Bot 所代表用户的 Cookie

### XSS Bot 的实现方案

#### 方案一：简单 HTTP 请求（如 curl）

- 使用 `curl` 或脚本直接请求页面
- 能触发 `<img>`、`<script src>` 等资源的自动加载
- 优点：实现简单
- 缺点：
  - 不会执行 JavaScript
  - 不会加载完整 DOM
  - 无法覆盖大多数 XSS 场景

这种方式更像是“带答案去验证”，不够真实。

#### 方案二：无头浏览器（推荐）

- 使用 Puppeteer、Selenium 等控制无头浏览器
- 会完整加载页面：
  - 执行 JavaScript
  - 渲染 DOM
  - 加载 CSS、图片等资源
- 能真实模拟用户访问行为

这是 CTF 和真实环境中最常见的 XSS Bot 实现方式。

### 回到开头的问题

- **CTF 中 XSS 是怎么执行的？**
  - 攻击者注入 payload → XSS Bot 访问页面 → 浏览器执行脚本

- **获取的 Cookie 是什么身份的用户？**
  - 取决于 Bot 模拟的是谁
  - 通常是管理员或高权限用户
  - 因此拿到的是管理员 Cookie，可直接用于登录后台

## XSS Bot 的作用

- **CTF 竞赛**
  - 自动访问选手提交的 payload
  - 检测是否成功窃取管理员 Cookie
  - 验证 XSS 漏洞是否可利用

- **安全测试**
  - 企业安全团队模拟用户行为
  - 检测网站是否存在 XSS 漏洞
  - 验证修复方案是否有效
